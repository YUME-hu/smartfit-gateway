# 实验 E2：端到端延迟（ACK 往返）

> 目的：回答"数据从手表到手机要多久"——毕业设计三大系统级验收里的**延迟**一条。
> 这一条比功耗更微妙：**必须先说清什么算"延迟"**，否则数字没有意义。

---

## 1. 指标定义：为什么测 RTT，而不是单向延迟

直觉的测法是这样：

```
手表在 t0 发出一帧 → 手机在 t1 收到 → 延迟 = t1 - t0
```

但 t0 和 t1 来自**两个不同的时钟**。要相减必须先做毫秒级对时，而我们的对时精度只有**秒级**
（PCF85063 是秒寄存器，且帧里的 `device_ts` 也只有秒）。所以单向延迟**在当前架构下不可测**。

因此本实验测的是 **RTT（round-trip time）**：

```
手表发出帧 (t0) → 手机收到 → 手机回 ACK → 手表收到 (t1)
延迟 = t1 - t0        ← 全程只用手表自己的时钟
```

**代价**：RTT 包含手机侧的处理时间（JS 桥 + GATT 写），严格说是"上行 + 手机处理 + 下行"的合计。
**论文里必须写成 RTT，不能写成"传输延迟"。**

---

## 2. 实验条件

| 项 | 值 |
| --- | --- |
| 日期 | 2026-11-24 23:5x |
| 设备 | ESP32-S3 手表 + Android 手机（App 前台） |
| 协议 | v2 二进制帧，停等 ACK |
| 采样率 | 每 5 秒 1 帧（一个窗口）→ 每分钟 12 个样本 |
| 测量点 | 固件在 ACK 写回调里取 `millis()`，精度 1ms |
| 环境 | 桌面近距（< 1m），无干扰源 |

---

## 3. 结果（n = 98，约 8 分钟）

| 指标 | 值 |
| --- | --- |
| **P50** | **169 ms** |
| **P95** | **232 ms** |
| 最大 | 316 ms |
| 平均 | 170 ms |
| 重传次数 | **0** |
| 放弃次数 | **0** |

样本随时间的稳定性（每 60 秒打印一次累计值）：

```
n=50   p50=162ms p95=232ms max=299ms
n=74   p50=168ms p95=240ms max=316ms
n=98   p50=169ms p95=232ms max=316ms
```

P50 在 162–169 ms 之间小幅波动，没有随时间漂移 → 链路稳定。

---

## 4. 这个 168ms 花在哪

| 组成 | 估算 | 说明 |
| --- | --- | --- |
| App 的 ACK 发送队列延时 | 40 ms | 我设的（见下），为了避开"回调内写 GATT"的坑 |
| BLE 连接间隔 × 2 | 60–100 ms | Android 默认连接间隔约 30–50 ms，一问一答各占一个间隔 |
| 手机侧 JS 桥 + GATT 写 | 20–40 ms | uni-app 的 JSBridge 开销 |
| 固件 drain 轮询 | 0–20 ms | `ringDrain()` 每 20ms 跑一次 |

**其中 40ms 是我们自己引入的**，可优化空间明确。

---

## 5. 修复前的对照（这才是这一节的价值）

在修好"GATT 就绪时序"之前，实测到的不是"慢"，而是**完全不工作**：

| 阶段 | 现象 | 等效延迟 |
| --- | --- | --- |
| 修复前 | 手机连上但一个字节都写不进来 → 固件等不到 ACK，每帧重传 3 次（1.5s/次）后放弃 | **≈ 4500 ms** |
| 修复后 | ACK 正常，0 重传 | **P50 168 ms** |

**关键教训**：修复前的 App 界面**一切正常**、数据也在流，只有固件侧的 `重传/放弃` 计数器能看出问题。
这就是为什么可靠性机制必须配**可观测的计数器**，否则"能用"和"正常工作"会长期混淆。

根因：Android 在连接刚建立时 GATT 尚未就绪，此时发起写会被**静默拒绝**（Promise 甚至可能 resolve）。
修法是连接后延后 600 ms 再发协议声明，并对写入重试 3 次。

## 6. 误差与局限（要主动交代）

1. **样本量小**：98 个点算 P95 实际只有约 5 个点落在尾部，统计意义有限；要更严谨至少需要上千样本
2. **单一机型**：只测了一台 Android 手机，不同厂商的 BLE 栈差异很大
3. **近距离**：桌面 < 1m，未测穿墙/远距离下的退化
4. **测量的插入效应**：RTT 本身包含 ACK 机制的开销（40ms 队列 + 一次下行），
   没有 ACK 时的真实上行延迟会更低
5. **未测"到云端可见"的延迟**：那是另一回事，受同步周期（15 分钟）支配，属于**数据新鲜度**而非链路延迟

---

## 7. 可优化项

| 优化 | 预期收益 |
| --- | --- |
| ACK 队列延时 40ms → 0（现在有重试兜底，可以试） | −30~40 ms |
| 请求高优先级连接间隔（`setBLEConnectionPriority`，Android 可到 11.25ms） | −40~60 ms |
| 固件改为事件驱动发送（收到新窗口立即 drain，不等 20ms 轮询） | −10 ms |

三项都做完，P50 有望进到 **80~100 ms**。
